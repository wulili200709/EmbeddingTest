# 多相机检测系统需求整理

## 1. 目标概述

在现有 `PySide6 + line2dup + ROI + embedding/traditional` 检测工具基础上，扩展为一个可用于现场运行的多相机检测系统。

系统需要同时支持两类界面：

- `运行界面`：面向产线操作员，只保留拍照、检测、结果显示、权限控制等必要功能。
- `调试界面`：面向工程调试人员，提供模板制作、ROI标注、算法调试、DI/DO调试、相机调试、参数配置等能力。

系统需要支持海康相机接入，按照已连接相机数量动态显示画面，最多支持 `4` 个相机同时显示。

## 2. 核心业务需求

### 2.1 多相机接入

- 支持接入海康相机。
- 相机数量根据实际连接情况动态识别。
- 运行界面中，连几个相机就显示几个相机画面。
- 第一版实际运行范围限制为 `1~2` 个相机。
- `cam1` 为最小有效运行链路，`cam2` 为可选增强链路。
- `0` 个相机时仅允许显示“未连接相机”状态，不允许启动检测。
- `1` 个相机时运行界面显示 `1` 个画面，最终结果由该相机下全部检测项直接汇总得到。
- `2` 个相机时运行界面显示 `2` 个画面，最终结果由 `cam1_result AND cam2_result` 得到。
- 第一版暂不实现 `3` / `4` 个相机的实际运行链路，但界面与模块结构可为后续扩展预留能力。
- 最多支持 `4` 个相机画面同时显示。
- 多相机显示建议采用多分屏布局：
  - `1` 个相机：单画面全屏或大画面显示
  - `2` 个相机：左右分屏
  - `3` 个相机：`2 + 1` 或 `2 x 2` 占位布局
  - `4` 个相机：`2 x 2` 四分屏

### 2.2 运行界面

运行界面尽量简洁，只保留生产运行必要信息。

包含内容：

- 相机实时画面区
- 当前产品信息
- 检测触发状态
- 每个 ROI 对应的检测项状态
- 总体检测结果
- 密码输入弹窗

运行界面规则：

- 每个 `ROI` 对应一个检测项。
- 在 `line2dup` 创建模板的 `reference roi` 界面中，画几个 ROI，就对应几个检测项。
- `reference roi` 中每个 ROI 除内部 `roi_label` 外，还应支持设置一个用于现场显示的 `display_name`。
- 该 `display_name` 由工程调试人员在 `reference roi` 阶段直接填写，运行界面右侧检测项列表优先显示该名称。
- 若某个 ROI 未设置 `display_name`，则运行界面退回显示其 `roi_label`。
- 这些检测项在运行界面中要一一显示。
- 运行界面右侧检测项状态区按检测项列表动态生成：新增一个 ROI/检测项，就新增一条对应的状态项。
- 每个检测项后面带一个状态指示灯：
  - 检测 `OK` 时亮绿灯
  - 检测 `NG` 时亮红灯
  - 未检测时可用灰灯
- 除每个检测项结果外，还要有一个总结果区域：
  - 总结果 `OK`：绿色显示
  - 总结果 `NG`：红色显示

### 2.3 NG 锁定与密码放行

运行界面中增加防误操作机制：

- 当本次总检测结果为 `NG` 时，系统进入锁定状态。
- 锁定状态下，不允许直接进行第二次检测。
- 必须弹出密码输入框。
- 只有密码输入正确后，才允许进行下一次检测。

建议补充规则：

- 密码正确后，仅获得 `1` 次放行资格。
- 这次放行资格只有在系统真正开始一次有效检测后才算被消耗，不是脚踏一踩就立即消耗。
- 密码错误时保留锁定状态。
- 建议记录密码放行日志，包括：
  - 时间
  - 当前产品
  - 操作员或账号
  - 上一次检测结果

### 2.4 调试界面

调试界面保留并继续扩展所有工程调试功能。

调试界面建议包含：

- 产品切换
- 相机连接/断开/取流测试
- 单帧采图
- 连续采图预览
- ROI 标注与模板制作
- `line2dup` 模板页
- 多 ROI 检测项配置
- embedding / traditional 算法训练与调试
- 单张测试 / 批量测试
- Margin 验证
- 传统基线调试
- DI 输入调试
- DO 输出调试
- 光源控制调试
- 三色灯输出调试
- 检测耗时监控

补充约束：

- 调试界面支持手动加载本地图片进行单张测试与批量测试
- 调试界面的“单帧采图”和“单张测试 / 批量测试”需要明确区分：
  - 单帧采图：从已连接相机抓取一张图用于调试
  - 单张测试 / 批量测试：从本地磁盘手动加载图片用于算法验证
- 手动加载本地图片测试仅属于调试界面能力，不进入运行界面
- 运行界面只处理现场相机采图、脚踏触发、结果显示和权限控制

### 2.5 DI / DO 交互

调试界面中增加 DI/DO 调试能力。

#### DI 输入

- 用于接收外部脚踏信号。
- 脚踏控制逻辑为：`DI` 信号由 `0` 变为 `1` 后，启动一次相机检测流程。
- 也就是只对脚踏信号的 `上升沿` 响应，不对持续高电平重复触发。

建议补充实现规则：

- 系统需要保存脚踏 DI 的上一时刻状态。
- 当检测到 `prev_di = 0` 且 `curr_di = 1` 时，认为发生一次有效触发。
- 当 `DI` 一直保持为 `1` 时，不重复启动检测。
- 只有当 `DI` 回到 `0` 后，下一次 `0 -> 1` 才允许再次触发。
- 若当前系统处于 `Capturing`、`Inspecting` 或 `LockedByNg` 状态，应忽略新的脚踏触发或记录为无效触发日志。

#### DO 输出

- 用于控制光源开关。
- 用于输出最终检测结果给三色灯或外部设备。

建议 DO 预留用途：

- `DO_LIGHT_CAM1`：相机1光源
- `DO_LIGHT_CAM2`：相机2光源
- `DO_RESULT_OK` 或三色灯绿
- `DO_RESULT_NG` 或三色灯红
- 也可以按现场实际 I/O 表重新映射

#### 三色灯 DO 控制流程

三色灯包含 `红 / 绿 / 蓝` 三个输出通道。

现场确认约束：

- 三色灯为低电平有效
- 光源 `DO` 极性暂未确认，不能默认与三色灯相同

控制逻辑如下：

- 开始检测前，亮 `蓝灯常亮`
- 进入检测状态后，三色灯全部熄灭
- 检测结果为 `OK` 时，闪 `绿灯`
- 检测结果为 `NG` 时，闪 `红灯`
- 在一定时间未检测时，恢复 `蓝灯常亮`

建议默认时序参数：

- `ok_flash_ms = 200`
- `ng_flash_ms = 200`
- `idle_blue_delay_ms = 30000`

建议定义为可配置参数：

- `blue_idle_enabled`
- `idle_blue_delay_ms`
- `ok_flash_ms`
- `ng_flash_ms`

推荐状态输出规则：

- `Idle / WaitingTrigger`
  - 蓝灯常亮
  - 红灯灭
  - 绿灯灭
- `Capturing / Inspecting`
  - 蓝灯灭
  - 红灯灭
  - 绿灯灭
- `Completed(OK)`
  - 绿灯亮 `ok_flash_ms`
  - 之后熄灭
  - 若后续持续无检测达到 `idle_blue_delay_ms`，蓝灯恢复常亮
- `Completed(NG)`
  - 红灯亮 `ng_flash_ms`
  - 之后熄灭
  - 若后续持续无检测达到 `idle_blue_delay_ms`，蓝灯恢复常亮

建议补充规则：

- 蓝灯表示“设备空闲、可触发”
- 系统一旦进入检测流程，蓝灯立即熄灭
- 结果灯优先级高于蓝灯，显示结果期间蓝灯不能同时亮
- 若现场要求更强提示，可支持 `OK/NG` 闪烁多次，但第一版建议先实现单次点亮
- 三色灯控制应统一由一个 `TowerLightController` 或 `IoManager` 子模块管理，避免界面代码直接拼接 DO 输出逻辑

## 3. 检测逻辑需求

### 3.1 ROI 与检测项映射关系

当前要求如下：

- 在 `line2dup` 的模板创建界面中，参考图上画多少个 ROI，就生成多少个检测项。
- 每个 ROI 必须与一个检测网络或检测逻辑一一对应。
- 运行界面中需要按照这个映射关系显示每个检测项的结果。

建议统一约定：

- 每个 ROI 使用唯一标识，例如：
  - `roi1`
  - `roi2`
  - `roi3`
- 每个 ROI 对应一个 `InspectionItem`
- 每个 `InspectionItem` 包含：
  - `item_id`
  - `item_name`
  - `camera_id`
  - `roi_label`
  - `algorithm_type`
  - `enabled`
  - `last_result`

### 3.2 多相机结果合并

一个产品可以由多个相机共同检测，但最终只输出一个产品结果。

规则：

- 每个相机可以负责若干 ROI 检测项。
- 每个检测项先独立得到 `OK/NG`
- 每个相机可得到一个相机级汇总结果
- 最终产品结果由所有相机结果进行逻辑 `AND`

即：

- 只要任意一个相机下任意一个检测项为 `NG`
- 则该产品总结果为 `NG`
- 只有所有相机、所有检测项都为 `OK`
- 最终总结果才为 `OK`

建议公式：

```text
item_result = 每个ROI的检测结果
camera_result = AND(该相机下全部 item_result)
final_result = AND(全部 camera_result)
```

### 3.3 运行时的检测顺序

收到脚踏 DI 信号后，系统启动一次完整检测流程。

建议流程：

1. 系统检查当前是否处于 `锁定` 状态
2. 若锁定且未密码放行，则禁止继续
3. 若检测到脚踏 `DI` 上升沿且允许检测，则开始本轮采图
4. 按相机顺序控制光源并拍照
5. 每台相机图像进入对应检测队列
6. 等待全部相机检测完成
7. 汇总所有 ROI 项结果
8. 生成产品总结果
9. 输出 DO 到三色灯
10. 若总结果为 `NG`，进入密码锁定状态

其中三色灯时序建议为：

1. `WaitingTrigger` 状态亮蓝灯常亮
2. 检测启动瞬间蓝灯熄灭
3. 检测完成后根据结果输出绿灯或红灯
4. 结果灯显示结束后全部熄灭
5. 若在 `idle_blue_delay_ms` 时间内没有再次检测，则恢复蓝灯常亮

## 4. 多相机拍照与光源时序

### 4.1 单相机场景

单相机时序要求相对简单：

1. 收到脚踏 DI
2. 打开该相机对应光源
3. 相机拍照
4. 检测算法运行
5. 检测完成后关闭光源
6. 输出结果

### 4.2 双相机场景

你提出的关键要求是：

- 如果算法耗时较长，不一定要等第一个相机算法检测结束，再拍第二个相机。
- 第一个相机拍完并灭第一路光源后，就可以启动第二路光源和第二个相机拍摄。
- 第二个相机拍摄和第一个相机算法计算可以并行。

建议双相机时序：

1. 收到脚踏 DI
2. 打开 `CAM1` 光源
3. `CAM1` 拍照取图
4. `CAM1` 图像立即送入检测线程
5. 关闭 `CAM1` 光源
6. 打开 `CAM2` 光源
7. `CAM2` 拍照取图
8. `CAM2` 图像立即送入检测线程
9. 关闭 `CAM2` 光源
10. 等待 `CAM1`、`CAM2` 检测都完成
11. 合并结果
12. 输出三色灯 DO

也就是说：

- `拍照阶段` 和 `算法阶段` 尽可能解耦
- 相机采图不要被前一张图的算法耗时阻塞
- 光源切换要确保互不冲突

### 4.3 推荐执行模型

建议采用以下流水线模型：

- `DI触发线程`：监听脚踏信号
- `采图调度线程`：负责按顺序打开光源、控制相机拍照、关闭光源
- `算法线程池`：负责各相机图像检测
- `主线程/UI线程`：负责显示画面、状态、灯色、结果
- `三色灯状态控制器`：负责蓝灯待机、检测中熄灯、结果闪灯、超时恢复蓝灯

推荐原则：

- 采图与算法异步
- 相机拍完立即把图像提交给检测线程
- 后续相机可继续拍摄，不阻塞
- 最终仅在“结果汇总”阶段等待全部检测完成

## 9. 推荐状态机

建议运行态增加明确状态机，避免后面逻辑越来越乱。

建议状态（与 `系统模块设计.md` 保持一致）：

- `WaitingTrigger`
- `CapturingCam1`
- `CapturingCam2`
- `Inspecting`
- `Aggregating`
- `CompletedOk`
- `CompletedNg`
- `LockedByNg`
- `Error`

> **说明**：`Completed` 拆分为 `CompletedOk` 和 `CompletedNg`，便于三色灯控制器直接映射状态，不再需要额外判断 result 字段。密码放行不作为独立状态，由 `PermissionManager.unlock_once()` 返回成功后，`InspectionScheduler` 直接将状态恢复到 `WaitingTrigger`。

状态切换：

```text
WaitingTrigger -> CapturingCam1
CapturingCam1  -> CapturingCam2
CapturingCam2  -> Inspecting
Inspecting     -> Aggregating
Aggregating    -> CompletedOk
Aggregating    -> CompletedNg
CompletedOk    -> WaitingTrigger
CompletedNg    -> LockedByNg
LockedByNg  (密码正确后) -> WaitingTrigger
任意状态异常   -> Error
```

三色灯状态与运行状态的推荐映射：

```text
WaitingTrigger:                          蓝灯常亮
CapturingCam1 / CapturingCam2:          全灭
Inspecting / Aggregating:               全灭
CompletedOk:                            绿灯亮 ok_flash_ms
CompletedNg:                            红灯亮 ng_flash_ms
LockedByNg:                             全灭（可选保留红灯）
WaitingTrigger 超过 idle_blue_delay_ms: 蓝灯常亮
```

## 10.1 海康 Python 示例调研结论

本项目已附带海康 Python 示例，重点参考了：

- `Python/BasicDemo/BasicDemo.py`
- `Python/BasicDemo/CamOperation_class.py`
- `Python/MultipleCameras/MultipleCameras.py`
- `Python/MultipleCameras/CamOperation_class.py`

从示例中可以确认以下实现事实，这些内容会直接影响后续正式系统设计。

### 海康示例中已经验证的能力

- 支持设备枚举
- 支持单相机打开/关闭
- 支持最多 `4` 路相机的界面显示
- 支持开始/停止抓流
- 支持连续模式
- 支持触发模式
- 支持软触发
- 支持硬触发源切换
- 支持曝光、增益、帧率参数设置
- 支持图像显示与存图

### 对正式项目最有价值的结论

- 多相机示例已经按 `4` 路上限设计，这和当前运行界面最多 `4` 相机的需求一致。
- 每个相机都维护一个独立的 `CameraOperation` 实例。
- 每个相机在开始抓流后都会启动自己的抓图线程。
- 示例通过 `MV_CC_GetImageBuffer` 从 SDK 取图，再调用 `MV_CC_DisplayOneFrame` 显示到对应窗口。
- 多相机示例中已经支持把触发源设置为：
  - `Software`
  - `Line0`

这意味着：

- 你后面脚踏信号如果是接到相机输入口并由相机硬触发，可以沿着 `TriggerSource = Line0` 这条路继续做。
- 如果脚踏信号接到 PLC / IO 卡，再由上位机统一调度，也可以先走“上位机收到 DI 上升沿，再控制相机软触发”的方式。

### 当前示例暴露出的架构约束

- 海康示例是 `PyQt5` 写的，而你当前主程序是 `PySide6`，后续整合时要统一为一个 UI 技术栈。
- 示例的显示方式偏 SDK Demo 风格，适合验证取图，不适合直接作为正式业务架构。
- 示例里的多相机抓图线程和 UI、业务逻辑耦合较近，正式项目中应进一步封装。
- 示例代码中“枚举设备 -> 用索引打开设备”的方式更适合 demo，正式项目建议改成“按序列号绑定逻辑相机”。

### 强烈建议增加的正式项目规则

- 相机逻辑编号不要直接依赖枚举顺序。
- 建议使用相机 `SerialNumber` 作为稳定绑定依据。
- 配置文件中应保存：
  - `camera_id`
  - `serial_number`
  - `display_name`
  - `light_do`
  - `trigger_source`
  - `exposure_time`
  - `gain`
  - `frame_rate`

推荐示例：

```text
Camera1 -> serial_number = DA3212345
Camera2 -> serial_number = DA3212346
```

这样可避免：

- 重启后枚举顺序变化
- 更换网口或 USB 口后相机顺序变化
- 现场维护时“相机1/相机2”错位

### 对抓图流程的直接启发

根据示例，后续正式项目建议把海康取图封装成如下层级：

- `HikCameraDevice`
  - 封装单台海康相机的打开、关闭、开始抓流、停止抓流、参数设置、软触发、取最新帧
- `HikCameraManager`
  - 负责设备枚举、按序列号匹配配置、维护多相机实例
- `FrameDispatcher`（已合并入 `HikCameraManager`）
  - 预览帧由 `HikCameraDevice.get_latest_preview()` 提供，运行界面通过 `RunViewModel` 订阅；正式检测帧由 `FrameGrabService` 统一管控，不需要独立的 FrameDispatcher 类

### 关于脚踏触发的两种实现路线

结合你当前需求和海康示例，后续可选两条路线：

#### 路线 A：上位机 DI 触发 + 相机软触发

流程：

1. 上位机监听脚踏 DI
2. 检测到 `0 -> 1` 上升沿
3. 上位机按时序控制光源
4. 上位机调用相机 `TriggerSoftware`
5. 取回图像并送检

优点：

- 逻辑集中在上位机，便于统一调度双相机时序
- 更容易和三色灯、密码锁定、检测状态机关联

缺点：

- 对上位机调度实时性有一定要求

#### 路线 B：脚踏直接触发相机硬触发输入

流程：

1. 脚踏信号进入相机 `Line0`
2. 相机自行曝光采图
3. 上位机从抓流线程中拿到对应帧
4. 再做检测和结果汇总

优点：

- 触发链路短
- 拍照时序更靠近相机底层

缺点：

- 多相机光源时序和脚踏联动会更复杂
- 不太适合你现在这种“相机1拍完再启相机2光源”的串行采图控制需求

因此，基于你当前描述的业务流程，第一版更推荐：

- `脚踏 DI 进上位机`
- `上位机调度 DO 光源`
- `上位机按顺序对相机执行软触发`

### 与你当前需求最匹配的建议

你的需求重点不是单纯“持续预览”，而是：

- 脚踏触发一次产品检测
- 有严格的光源切换时序
- 双相机采图尽量快
- 算法与采图可并行
- 最终要和三色灯、密码放行、运行界面结果联动

所以不建议直接照搬 Demo 的“连续抓流 + UI显示”模式作为正式运行逻辑。

更适合的正式架构是：

- 平时可选低帧率预览或不预览
- 真正检测时走一次明确的 `Trigger -> Grab -> Dispatch -> Inspect -> Aggregate -> Output`
- 运行界面的多画面主要显示“最近一次图像”或“低频实时预览”
- 正式检测图像由调度器明确管理，不依赖 UI 显示线程

## 12. 我对需求的补充建议

### 12.1 强烈建议先定义“配置驱动”

后面你会有：

- 多产品
- 多相机
- 多 ROI
- 多算法
- 多 IO 点位

如果这些关系不先配置化，后面代码会非常难维护。

### 12.2 强烈建议把“采图”和“检测”分线程

这是你这个系统后面能否跑顺的关键点。

特别是双相机时：

- `CAM1` 拍完立即提交算法线程
- 主调度继续拍 `CAM2`
- 不要等 `CAM1` 算法结束后再拍 `CAM2`

这样才能缩短节拍。

### 12.3 强烈建议把运行界面和调试界面彻底分开

原因：

- 操作员不需要看到复杂参数
- 现场误操作风险低
- UI 逻辑更清晰
- 代码结构更容易维护

### 12.4 建议为每个 ROI 增加“显示名称”

不要只用 `roi1/roi2/roi3`

建议同时保存：

- `roi_label`: 程序内部标识
- `display_name`: 运行界面显示名称

第一版要求明确为：

- 在 `Reference ROI` 界面画框或编辑 ROI 时，应允许直接设置 `display_name`
- `display_name` 随 `line2dup_recipe.json` 一起保存
- `InspectionItem.display_name` 默认继承自该字段
- 运行界面右侧检测项状态列表优先显示 `display_name`
- 未填写 `display_name` 时，退回显示 `roi_label`

例如：

- `roi1` -> `瓶盖颜色`
- `roi2` -> `标签缺损`

### 12.5 建议先支持 `2` 相机，架构上兼容 `4` 相机

你的当前需求重点在双相机联动和节拍控制。

推荐做法：

- 第一版先把 `2` 相机跑通
- 但界面和配置设计时按最多 `4` 相机设计

这样避免一开始就把复杂度拉太高。

- 海康相机是软触发还是外触发？
