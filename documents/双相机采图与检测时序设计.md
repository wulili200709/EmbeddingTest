# 双相机采图与检测时序设计

## 1. 文档目标

本文档用于细化双相机场景下的实际执行流程，重点描述：

- 脚踏 `DI` 上升沿触发后的处理顺序
- 双相机光源切换与拍照顺序
- 采图与算法并行的实现建议
- 三色灯 `DO` 输出时序
- `NG` 锁定与密码放行的插入点

本文档默认基于以下前提：

- 使用海康相机
- 第一版运行范围为 `1~2` 个相机
- `cam1` 为最小有效运行链路，`cam2` 为可选增强链路
- `0` 个相机时仅允许显示未连接状态，不允许启动检测
- `1` 个相机时运行界面显示 `1` 个画面，最终结果由该相机结果直接给出
- `2` 个相机时运行界面显示 `2` 个画面，最终结果由双相机结果做逻辑 `AND`
- 第一版优先采用 `上位机接收 DI -> 上位机控制光源 -> 上位机软触发相机`
- 运行界面和调试界面分离

## 2. 参与模块

建议系统中至少包含以下运行时模块：

- `DiMonitor`
  - 监听脚踏输入
- `InspectionScheduler`
  - 负责任务调度与状态流转
- `LightController`
  - 控制 `CAM1` / `CAM2` 光源
- `HikCameraManager`
  - 管理海康相机实例
- `FrameGrabService`
  - 发起软触发并获取单次拍照结果
- `InspectionExecutor`
  - 执行每个相机对应 ROI 的检测逻辑
- `ResultAggregator`
  - 合并每个 ROI、每个相机以及总结果
- `TowerLightController`
  - 控制三色灯
- `PermissionManager`
  - 管理 `NG` 锁定和密码放行
- `RunViewModel`
  - 给运行界面推送状态、图像和结果

## 3. 状态定义

建议运行态采用以下状态：

- `WaitingTrigger`
  - 空闲待机，可触发
- `CapturingCam1`
  - 相机1采图中
- `CapturingCam2`
  - 相机2采图中
- `Inspecting`
  - 至少有一台相机算法执行中
- `Aggregating`
  - 汇总各检测项结果
- `CompletedOk`
  - 本轮产品结果为 `OK`
- `CompletedNg`
  - 本轮产品结果为 `NG`
- `LockedByNg`
  - `NG` 后锁定，等待密码放行
- `Error`
  - 采图、IO、检测、结果输出中出现异常

## 4. 单次检测总流程

一次完整检测任务建议定义为一个 `InspectionTask`，包含：

- `task_id`
- `trigger_timestamp`
- `product_name`
- `camera_images`
- `camera_results`
- `final_result`
- `elapsed_ms`

完整流程如下：

1. `DiMonitor` 检测到脚踏 `DI` 由 `0 -> 1`
2. `InspectionScheduler` 判断当前是否允许触发
3. 若允许，则创建新的 `InspectionTask`
4. `TowerLightController` 熄灭蓝灯
5. 按顺序执行 `CAM1`、`CAM2` 采图
6. 每台相机拍到图后立即提交给 `InspectionExecutor`
7. `InspectionExecutor` 对两台相机的图像并行检测
8. `ResultAggregator` 汇总 ROI 结果、相机结果、最终结果
9. `TowerLightController` 根据最终结果输出绿灯或红灯
10. 若结果为 `NG`，进入 `LockedByNg`
11. 若结果为 `OK`，恢复待机状态
12. 若长时间无检测，恢复蓝灯常亮

## 5. 脚踏触发时序

### 5.1 触发判定规则

脚踏只响应上升沿：

```text
prev_di = 0 且 curr_di = 1 -> 触发一次检测
prev_di = 1 且 curr_di = 1 -> 不触发
prev_di = 1 且 curr_di = 0 -> 仅表示释放，不触发
```

### 5.2 触发屏蔽规则

以下状态不允许再次响应脚踏：

- `CapturingCam1`
- `CapturingCam2`
- `Inspecting`
- `Aggregating`
- `LockedByNg`

建议行为：

- 直接忽略新的脚踏输入
- 或记录一条“触发被忽略”的运行日志

### 5.3 去抖建议

现场脚踏开关可能抖动，建议增加一个简单去抖时间：

- `di_debounce_ms = 30 ~ 100`

推荐规则：

- 检测到 `0 -> 1` 后，延迟一个很短的去抖时间
- 若仍为 `1`，确认触发有效

## 6. 双相机采图时序

## 6.1 设计原则

你的要求核心是：

- 相机1拍完后，不必等待相机1算法完成
- 相机1灭灯后，立即可以开始相机2光源和拍照
- 相机2采图和相机1算法可以并行

因此采图与算法必须解耦。

### 6.2 推荐时序

推荐顺序如下：

1. 收到脚踏 `DI` 上升沿
2. 状态切到 `CapturingCam1`
3. 熄灭蓝灯
4. 打开 `CAM1` 光源
5. 等待光源稳定时间 `light_stable_ms`
6. 触发 `CAM1` 拍照
7. 成功取到 `CAM1` 图像
8. 关闭 `CAM1` 光源
9. 将 `CAM1` 图像立即提交到算法线程池
10. 状态切到 `CapturingCam2`
11. 打开 `CAM2` 光源
12. 等待光源稳定时间 `light_stable_ms`
13. 触发 `CAM2` 拍照
14. 成功取到 `CAM2` 图像
15. 关闭 `CAM2` 光源
16. 将 `CAM2` 图像立即提交到算法线程池
17. 状态切到 `Inspecting`
18. 等待 `CAM1` 与 `CAM2` 对应任务全部完成
19. 状态切到 `Aggregating`
20. 汇总结果并输出最终结果

### 6.3 双相机时序图

```text
时间轴 ->

脚踏DI:        0 ---- 1 ---------------------------------------------------

蓝灯:          常亮 ---- 熄灭 -------------------------------------- 待机恢复

CAM1光源:      off ----- on ---- off --------------------------------------
CAM1拍照:             [ trigger + grab ]
CAM1算法:                     [----------- inspect cam1 -----------]

CAM2光源:      off ---------------- on ---- off ----------------------------
CAM2拍照:                          [ trigger + grab ]
CAM2算法:                                  [------ inspect cam2 ------]

结果汇总:                                                     [aggregate]

三色灯结果:                                                     [OK/NG]
```

### 6.4 关键点

- `CAM2` 拍照开始时间只依赖 `CAM1` 是否拍完和灭灯
- `CAM2` 拍照不依赖 `CAM1` 算法是否完成
- 算法线程池可以同时执行两个相机的检测任务
- 汇总阶段才需要等待所有算法结果齐全

## 7. 线程模型建议

### 7.1 推荐线程分工

- `UI线程`
  - 只做界面显示、按钮交互、状态更新
- `DI监听线程`
  - 轮询或阻塞读取脚踏 DI
- `采图调度线程`
  - 负责按顺序控制光源、软触发相机、拉取图像
- `算法线程池`
  - 每张图提交一个任务执行检测
- `IO输出线程` 或定时器
  - 管理三色灯闪烁和超时恢复

### 7.2 不建议的做法

- 不要在 UI 主线程里直接等待相机取图
- 不要在 UI 主线程里直接执行检测算法
- 不要让光源控制逻辑分散在多个界面按钮事件中
- 不要让相机预览线程直接承担“正式检测任务状态流转”

## 8. 三色灯时序设计

### 8.1 状态映射

- `WaitingTrigger`
  - 蓝灯常亮
- `CapturingCam1 / CapturingCam2 / Inspecting / Aggregating`
  - 三灯全灭
- `CompletedOk`
  - 绿灯亮
- `CompletedNg`
  - 红灯亮
- `LockedByNg`
  - 可保持全灭，或根据现场需要保留红灯提示

### 8.2 推荐时序参数

- `ok_flash_ms = 200`
- `ng_flash_ms = 200`
- `idle_blue_delay_ms = 30000`
- `light_stable_ms = 20 ~ 100`

### 8.3 推荐输出顺序

#### OK 结果

1. 检测开始前蓝灯常亮
2. 开始检测时蓝灯熄灭
3. 总结果 `OK`
4. 绿灯亮 `ok_flash_ms`
5. 绿灯熄灭
6. 若后续 `idle_blue_delay_ms` 内没有再次检测，蓝灯恢复常亮

#### NG 结果

1. 检测开始前蓝灯常亮
2. 开始检测时蓝灯熄灭
3. 总结果 `NG`
4. 红灯亮 `ng_flash_ms`
5. 红灯熄灭
6. 系统进入 `LockedByNg`
7. 解除锁定并回到待机后，若超过 `idle_blue_delay_ms` 无检测，蓝灯恢复常亮

## 9. NG 锁定与密码放行时序

### 9.1 NG 后的标准流程

1. 双相机检测完成
2. 最终总结果为 `NG`
3. 三色灯输出红灯
4. 当前任务结束
5. 系统状态切换到 `LockedByNg`
6. 运行界面立即弹出密码输入框
7. 后续脚踏触发无效
8. 锁定期间继续踩脚踏也不能启动下一轮检测
9. 密码正确后，状态回到 `WaitingTrigger`，并带有“放行一次但尚未消耗”的标记
10. 操作员再次踩脚踏后，系统先进行前置校验
11. 只有当系统真正开始一次有效检测时，这次放行资格才算被消耗
12. 若前置校验失败、设备未就绪、配置缺失、采图未成功触发，则本次放行资格继续保留
13. 若放行后的这次有效检测仍为 `NG`，再次进入 `LockedByNg` 并再次弹出密码框

### 9.2 推荐密码策略

- 密码放行只生效一次
- 这“一次”是指“一次真正开始的有效检测”，不是“踩一次脚踏”
- 一次放行后，下一次若再出现 `NG`，重新锁定
- 密码输入错误不改变锁定状态
- 建议记录密码放行日志
- 该策略只在`运行界面`生效，调试界面不启用

## 10. 结果汇总逻辑

### 10.1 检测项级结果

每个 ROI 对应一个检测项：

```text
item_result = OK / NG
```

### 10.2 相机级结果

每台相机的结果由其下全部 ROI 项进行 `AND`：

```text
camera1_result = AND(camera1_item_1, camera1_item_2, ...)
camera2_result = AND(camera2_item_1, camera2_item_2, ...)
```

### 10.3 产品级结果

最终总结果：

```text
final_result = AND(camera1_result, camera2_result)
```

只要任意一项为 `NG`，总结果即为 `NG`。

## 11. 异常处理建议

以下情况建议统一按 `NG` 处理，并记录错误原因：

- `CAM1` 采图失败
- `CAM2` 采图失败
- 光源打开失败
- 触发命令失败
- 图像为空
- ROI 缺失
- 算法执行异常
- 结果汇总异常
- 三色灯输出失败

推荐行为：

1. 标记本轮检测结果为 `NG`
2. 记录错误代码与错误消息
3. 输出红灯
4. 进入 `LockedByNg` 或 `Error`

建议区分：

- `业务NG`
  - 图像正常、算法正常、结果判定为不良
- `系统异常NG`
  - 取图、IO、算法执行异常导致无法完成正常判定

运行界面最好能区分这两种情况。

## 12. 第一版落地建议

为了尽快跑通，推荐第一版做法如下：

### 12.1 范围控制

- 先做 `2` 个相机
- 先做 `脚踏 DI -> 上位机软触发`
- 先做每相机拍 1 张图
- 先做结果灯单次点亮，不做复杂闪烁模式
- 先做 `NG` 后必须密码放行
- 先做每产品一条测试记录
- 先做每天一个 `csv` 结果文件

### 12.2 推荐实现顺序

1. 打通海康双相机枚举、按序列号绑定、打开关闭
2. 做单次软触发取图接口
3. 做双相机顺序采图调度
4. 做两张图并行送检
5. 做结果汇总与运行界面显示
6. 做三色灯输出
7. 做 `NG` 锁定和密码放行
8. 最后再补连续预览、DI/DO 调试页和更多异常恢复

## 13. 伪代码参考

```python
from concurrent.futures import ThreadPoolExecutor, wait, ALL_COMPLETED

def on_di_rising_edge():
    if not scheduler.can_start_inspection():
        return

    task = scheduler.create_task()
    tower_light.enter_inspecting()

    img1 = capture_with_light(camera_id="cam1", light_do="light_cam1")
    future1 = executor.submit(camera_id="cam1", image=img1, task_id=task.id)

    img2 = capture_with_light(camera_id="cam2", light_do="light_cam2")
    future2 = executor.submit(camera_id="cam2", image=img2, task_id=task.id)

    # 使用 wait() 并发等待，不依赖固定顺序，cam2 先完成也不会被阻塞
    done, _ = wait([future1, future2], return_when=ALL_COMPLETED)

    result1 = future1.result()
    result2 = future2.result()

    final_result = aggregate(result1, result2)
    update_run_ui(task, result1, result2, final_result)

    if final_result == "OK":
        tower_light.show_ok()
        scheduler.enter_waiting_trigger()
    else:
        tower_light.show_ng()
        permission_manager.lock_by_ng()
```

> **说明**：之前直接串行调用 `wait_result(cam1)` 再 `wait_result(cam2)`，如果 cam1 算法慢而 cam2 已完成，仍会白白等待 cam1 才能继续。改为 `concurrent.futures.wait([future1, future2])` 后，等待是并发的，哪个先完成都没有影响，汇总阶段再统一取结果。

## 14. 后续可扩展点

本设计后续可平滑扩展到：

- 最多 `4` 相机
- 每相机多个 ROI
- 每个 ROI 不同算法
- 相机硬触发
- PLC 联动
- 三色灯更复杂闪烁策略
- 历史记录和追溯

扩展时建议仍保持：

- 采图调度独立
- 算法线程池独立
- IO 控制独立
- UI 只做显示，不做阻塞业务
