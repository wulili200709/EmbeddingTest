# 系统模块设计

## 1. 文档目的

本文档用于把前两份需求文档进一步收敛为可开发的软件模块设计，重点明确：

- 系统分层
- 主要模块职责
- 关键类与数据结构
- 模块之间的数据流
- 推荐目录结构

本文档默认面向第一版目标：

- 支持 `2` 台海康相机
- 运行界面与调试界面分离
- 脚踏 `DI` 上升沿触发检测
- 双相机顺序采图、算法并行
- 检测结果控制三色灯
- `NG` 后密码放行

## 2. 总体架构

建议整体按四层拆分：

- `UI层`
  - 运行界面
  - 调试界面
- `应用调度层`
  - 检测流程调度
  - 状态机
  - 权限控制
- `领域服务层`
  - 相机管理
  - 采图服务
  - 检测执行
  - 结果汇总
  - 配方管理
  - IO 控制
- `基础设施层`
  - 海康 SDK 封装
  - DI/DO 驱动封装
  - 文件配置读写
  - 日志与历史记录

建议架构关系：

```text
UI层
  -> 应用调度层
      -> 领域服务层
          -> 基础设施层
```

原则：

- UI 不直接操作 SDK
- UI 不直接写 DI/DO
- UI 不直接运行检测算法
- 所有外设访问都统一下沉到服务层或基础设施层

## 3. 模块划分

### 3.1 UI 层

建议拆成两个主窗口：

- `RunMainWindow`
  - 面向运行
- `DebugMainWindow`
  - 面向调试

#### `RunMainWindow`

职责：

- 显示多相机画面
- 显示每个 ROI 对应检测项状态
- 显示总结果
- 显示当前产品、系统状态、锁定状态
- 响应密码输入框

不负责：

- 直接调用海康 SDK
- 直接控制光源
- 直接触发检测流程
- 直接做模型推理

#### `DebugMainWindow`

职责：

- 产品切换
- ROI 标注与模板编辑
- 检测项配置
- 相机调试
- DI/DO 调试
- 训练、测试、报表分析

建议保留你现有 `qr_gui_pyside6.py` 的大部分功能作为调试界面基础，但逐步拆到独立子页中。

### 3.2 应用调度层

建议包括：

- `InspectionScheduler`
- `PermissionManager`
- `RunStateMachine`
- `RunViewModel`

#### `InspectionScheduler`

职责：

- 接收脚踏触发事件
- 判断当前是否允许启动检测
- 创建 `InspectionTask`
- 串起采图、检测、汇总、输出全过程
- 管理一次完整检测任务的生命周期

核心特点：

- 是整个运行逻辑的总协调者
- 不直接做底层相机接口调用细节
- 不直接做 UI 绘制

#### `PermissionManager`

职责：

- 管理 `NG` 锁定状态
- 管理密码放行
- 提供“当前是否允许再次检测”的判断

建议接口：

- `is_locked() -> bool`
- `lock_by_ng() -> None`
- `unlock_once(password: str) -> bool`
- `can_start_inspection() -> bool`

#### `RunStateMachine`

职责：

- 管理运行态的状态切换
- 保证状态转换合法
- 给 UI 和三色灯控制器提供统一状态来源

建议状态：

- `WaitingTrigger`
- `CapturingCam1`
- `CapturingCam2`
- `Inspecting`
- `Aggregating`
- `CompletedOk`
- `CompletedNg`
- `LockedByNg`
- `Error`

状态通知机制：

- `RunStateMachine` 内部维护当前状态，状态变更时通过回调（或 `PySide6 Signal`）通知 `RunViewModel`
- `TowerLightController` 也直接订阅同一个状态变更事件，不需要 `InspectionScheduler` 报告两次
- `InspectionScheduler` 负责调用 `state_machine.transition(new_state)`，不直接操作灯或界面

#### `RunViewModel`

职责：

- 将调度层产出的状态、图片、检测项结果整理为 UI 友好的数据
- 向运行界面发送更新信号

建议内容：

- 当前状态文本
- 当前产品名
- 每相机最新图像
- 每个检测项的状态
- 总结果
- 锁定状态
- 相机连接状态

### 3.3 领域服务层

建议包括：

- `HikCameraManager`
- `HikCameraDevice`
- `FrameGrabService`
- `InspectionExecutor`
- `InspectionItemManager`
- `ResultAggregator`
- `RecipeManager`
- `IoManager`
- `LightController`
- `TowerLightController`
- `DiMonitor`

## 4. 核心模块详细设计

### 4.1 `HikCameraManager`

职责：

- 枚举所有海康相机
- 按 `SerialNumber` 与配置文件绑定逻辑相机
- 创建和维护多个 `HikCameraDevice`
- 统一打开、关闭、配置所有相机

建议接口：

- `scan_devices() -> list[CameraDescriptor]`
- `bind_from_recipe(recipe) -> None`
- `open_all() -> None`
- `close_all() -> None`
- `get_camera(camera_id: str) -> HikCameraDevice`
- `connected_cameras() -> list[str]`

设计建议：

- 逻辑相机编号例如 `cam1`、`cam2`
- 物理相机识别依据应为 `serial_number`
- 不依赖枚举顺序

### 4.2 `HikCameraDevice`

职责：

- 封装单台海康相机的所有 SDK 操作

建议能力：

- 打开 / 关闭
- 开始抓流 / 停止抓流
- 设置连续模式 / 触发模式
- 设置软触发 / `Line0`
- 设置曝光 / 增益 / 帧率
- 获取单帧图像
- 获取预览帧

建议接口：

- `open() -> None`
- `close() -> None`
- `start_grabbing() -> None`
- `stop_grabbing() -> None`
- `set_trigger_mode(mode: str) -> None`
- `set_trigger_source(source: str) -> None`
- `soft_trigger() -> None`
- `grab_one(timeout_ms: int) -> FramePacket`
- `get_latest_preview() -> Optional[FramePacket]`

### 4.3 `FrameGrabService`

职责：

- 统一封装“正式检测取图”流程
- 控制光源稳定等待时间
- 触发拍照并拿到图像
- 向上层返回标准化图像数据

建议接口：

- `capture_with_light(camera_id: str, light_channel: str) -> FramePacket`
- `capture_sequence(camera_ids: list[str]) -> dict[str, FramePacket]`

返回建议：

- 图像矩阵
- 宽高
- 帧号
- 时间戳
- camera_id
- 是否成功
- 错误信息

### 4.4 `InspectionExecutor`

职责：

- 接收某个相机的一张图像
- 查出该相机下所有检测项
- 对这些 ROI 逐项执行检测
- 产出该相机的检测结果

建议特点：

- 背后用线程池或任务池
- 一个相机一张图对应一个检测任务
- 不阻塞采图调度线程

建议接口：

- `submit(task_id: str, camera_id: str, frame: FramePacket) -> Future`
- `wait_camera_result(task_id: str, camera_id: str) -> CameraInspectionResult`

### 4.5 `InspectionItemManager`

职责：

- 管理 ROI 与检测项之间的映射关系
- 维护每个检测项所属相机、算法类型、阈值、模型路径

建议接口：

- `load_items(product_name: str) -> list[InspectionItem]`
- `items_for_camera(camera_id: str) -> list[InspectionItem]`
- `enabled_items() -> list[InspectionItem]`

### 4.6 `ResultAggregator`

职责：

- 合并 ROI 结果
- 合并相机结果
- 生成最终总结果

建议接口：

- `aggregate_camera(item_results: list[ItemResult]) -> CameraInspectionResult`
- `aggregate_final(camera_results: list[CameraInspectionResult]) -> FinalInspectionResult`

规则：

- 单项结果：`OK/NG`
- 相机结果：相机下所有项 `AND`
- 产品结果：所有相机结果 `AND`

### 4.7 `RecipeManager`

职责：

- 管理产品、模板、模型、相机绑定、ROI 配置
- 作为“配置驱动”的统一入口

建议保存内容：

- 产品名称
- 相机配置
- 光源映射
- DI/DO 映射
- ROI 列表
- 检测项列表
- 模型路径
- 阈值参数

> **说明**：密码策略（`RunPassword`、`EngineerPassword`）不应放入产品配方，否则切换产品时密码也会跟着变。密码配置建议放在独立的系统级配置文件（例如 `config/system.yaml`）中，由 `PermissionManager` 在启动时加载，与产品配方完全分离。

建议接口：

- `load_product(product_name: str) -> ProductRecipe`
- `save_product(recipe: ProductRecipe) -> None`
- `list_products() -> list[str]`

### 4.8 `IoManager`

职责：

- 提供统一 DI/DO 访问接口
- 屏蔽底层 IO 驱动实现差异

建议接口：

- `read_di(channel: str) -> int`
- `write_do(channel: str, value: int) -> None`
- `read_all_di() -> dict[str, int]`
- `read_all_do() -> dict[str, int]`

### 4.9 `DiMonitor`

职责：

- 监听脚踏开关
- 做上升沿检测
- 做去抖
- 将有效触发事件发送给 `InspectionScheduler`

建议接口：

- `start() -> None`
- `stop() -> None`
- `on_di_changed(value: int) -> None`

### 4.10 `LightController`

职责：

- 控制相机光源开关
- 封装光源稳定等待逻辑

建议接口：

- `light_on(camera_id: str) -> None`
- `light_off(camera_id: str) -> None`
- `prepare_capture(camera_id: str) -> None`
- `finish_capture(camera_id: str) -> None`

### 4.11 `TowerLightController`

职责：

- 控制蓝灯待机
- 控制检测中灭灯
- 控制 `OK` 绿灯输出
- 控制 `NG` 红灯输出
- 管理超时恢复蓝灯

建议接口：

- `enter_waiting() -> None`
- `enter_inspecting() -> None`
- `show_ok() -> None`
- `show_ng() -> None`
- `clear() -> None`

### 4.12 `PermissionManager`

职责前面已定义，这里补充建议实现：

- 密码策略不要写死在 UI
- 支持后续扩展多级权限
- 放行日志建议统一写文件或数据库

## 5. 数据对象设计

建议使用 `dataclass` 或等价结构定义核心对象。

### 5.1 `CameraConfig`

```python
@dataclass
class CameraConfig:
    camera_id: str
    display_name: str
    serial_number: str
    trigger_source: str
    exposure_time: float
    gain: float
    frame_rate: float
    light_do: str
    enabled: bool = True
```

### 5.2 `InspectionItem`

```python
@dataclass
class InspectionItem:
    item_id: str
    item_name: str
    camera_id: str
    roi_label: str
    algorithm_type: str
    threshold: float | None = None
    model_path: str = ""
    enabled: bool = True
```

### 5.3 `FramePacket`

```python
@dataclass
class FramePacket:
    camera_id: str
    timestamp: float
    frame_no: int
    image: object
    width: int
    height: int
    ok: bool
    error: str = ""
```

### 5.4 `ItemResult`

```python
@dataclass
class ItemResult:
    item_id: str
    item_name: str
    camera_id: str
    roi_label: str
    result: str
    score: float | None = None
    error: str = ""
```

### 5.5 `CameraInspectionResult`

```python
@dataclass
class CameraInspectionResult:
    camera_id: str
    result: str
    item_results: list[ItemResult]
    elapsed_ms: float
    error: str = ""
```

### 5.6 `FinalInspectionResult`

```python
@dataclass
class FinalInspectionResult:
    task_id: str
    result: str
    camera_results: list[CameraInspectionResult]
    elapsed_ms: float
    error: str = ""
```

## 6. 模块间数据流

建议数据流如下：

```text
DiMonitor
  -> InspectionScheduler
      -> PermissionManager
      -> RunStateMachine
      -> TowerLightController
      -> FrameGrabService
          -> LightController
          -> HikCameraManager
              -> HikCameraDevice
      -> InspectionExecutor
          -> InspectionItemManager
          -> 现有算法模块(qr_core / traditional / line2dup)
      -> ResultAggregator
      -> RunViewModel
          -> RunMainWindow
```

## 7. 与现有代码的关系

### 7.1 现有 `qr_gui_pyside6.py`

建议定位为：

- 第一阶段继续作为 `调试界面原型`
- 后续逐步拆分为多个独立模块和页面

不建议继续做法：

- 把运行界面、多相机、DI/DO、三色灯、密码锁定继续全部塞进当前 `MainWindow`

### 7.2 现有算法模块

建议保留并复用：

- `qr_core`
- `traditional_algorithms`
- `line2dup_locator`
- `line2dup_recipe`

新系统只需要做一层“任务调度适配”，不需要先重写算法。

## 9. 第一版开发顺序建议

建议按以下顺序推进：

1. 先抽出 `dto.py`
2. 再抽出 `recipe_manager.py`
3. 再抽出 `hik_camera_device.py` 与 `hik_camera_manager.py`
4. 再做 `io_manager.py`、`light_controller.py`、`tower_light_controller.py`
5. 再做 `inspection_item_manager.py`
6. 再做 `inspection_executor.py`
7. 再做 `inspection_scheduler.py`
8. 最后做 `run_main_window.py`

原因：

- 先把数据结构和外设接口稳定住
- 再做流程调度
- 最后接 UI，返工最少

## 10. 第一版暂不建议做得太复杂的点

- 不要一开始就做 4 相机全支持
- 不要一开始就做复杂 PLC 协议
- 不要一开始就做多级用户系统
- 不要一开始就做太复杂的灯闪烁动画
- 不要一开始就把预览、检测、历史追溯、统计报表全部耦合到同一线程

## 11. 后续演进路线

当前设计未来可以继续扩展到：

- `4` 相机
- 相机硬触发
- PLC 联动
- 历史检测记录
- 图片归档
- 用户权限分级
- 设备健康监控
- 自动重连
- 工艺节拍统计

扩展时建议坚持两条原则：

- 运行调度逻辑集中在 `InspectionScheduler`
- 所有设备访问都通过独立模块完成
