# 整机总体需求文档

## 1. 文档目的

本文档用于作为后续开发的总需求基线，统一整理以下内容：

- 多相机检测业务需求
- 运行界面与调试界面的功能边界
- 海康相机接入方式
- 脚踏 `DI` 与三色灯 `DO` 控制逻辑
- `NKDIOLC_SDK` 对 DI/DO 与光源控制的实际约束
- 第一版开发范围与待确认事项

这份文档优先级高于零散讨论，后续代码开发默认以本文档为准。

## 2. 当前目标

在现有 `PySide6 + ROI标注 + line2dup + embedding/traditional` 项目基础上，扩展为一个可用于现场运行的工业检测软件。

系统目标：

- 第一版支持 `1~2` 个相机运行，后续可扩展到最多 `4` 相机
- 支持运行界面与调试界面分离
- 支持脚踏触发检测
- 支持三色灯结果反馈
- 支持光源控制
- 支持 `NG` 锁定与密码放行
- 支持多 ROI 对应多个检测项
- 支持一个产品由多个相机共同检测，最终只输出一个总结果

## 3. 系统组成

整机系统建议由以下部分组成：

- 上位机软件
- 海康工业相机
- 光源控制器
- DI/DO 控制板卡
- 三色灯
- 脚踏开关

其中上位机软件负责：

- 相机采图
- 检测任务调度
- ROI 对应检测项执行
- 检测结果汇总
- 运行界面显示
- 调试界面操作
- 光源控制
- 三色灯控制
- 脚踏输入监听
- 密码放行逻辑

## 4. 界面需求

### 4.1 运行界面

运行界面面向产线操作员，要求界面尽量简洁，只显示必要信息。

必须包含：

- 多相机画面显示区
- 每个检测项状态区
- 总结果显示区
- 当前产品信息
- 相机连接状态
- 系统状态
- 锁定状态
- 密码输入弹窗

运行界面要求：

- 连几个相机就显示几个画面
- 最多支持 `4` 分屏
- 一个 ROI 对应一个检测项
- 每个检测项后面有状态灯
- `OK` 亮绿灯
- `NG` 亮红灯
- 未检测显示灰色

总结果显示要求：

- 总结果 `OK` 时绿色显示
- 总结果 `NG` 时红色显示
- 总结果由全部相机结果做逻辑 `AND`

### 4.2 调试界面

调试界面面向工程人员，保留完整配置与调试能力。

建议包含页签：

- 产品/配方
- ROI 标注与模板页
- 检测项配置
- 相机调试
- 单帧采图
- 连续预览
- 训练与测试
- Margin 分析
- 传统算法调试
- DI/DO 调试
- 光源调试
- 运行监控
- 日志与报表

补充说明：

- 调试界面应支持手动加载本地图片进行单张测试与批量测试
- 调试界面的“单帧采图”与“手动加载图片测试”属于两类不同能力：
  - 单帧采图：图像来源于相机
  - 单张测试 / 批量测试：图像来源于本地磁盘文件
- 运行界面不提供手动加载本地图片入口，只处理相机实时采图与脚踏触发检测

现有 `EmbeddingTest/qr_gui_pyside6.py` 建议后续作为调试界面的基础原型，不建议继续承担运行界面职责。

## 5. 检测业务逻辑

### 5.1 ROI 与检测项

在 `line2dup` 模板创建界面的参考图中，画几个 ROI，就对应几个检测项。

要求：

- 每个 ROI 有唯一标识，例如 `roi1`、`roi2`
- 每个 ROI 对应一个检测项
- 每个检测项可以绑定到某一个相机
- 每个检测项可配置算法类型、阈值、模型路径
- 在 `reference roi` 阶段应支持为每个 ROI 设置 `display_name`
- `InspectionItem.display_name` 默认继承对应 ROI 的 `display_name`
- 运行界面右侧检测项状态区优先显示 `display_name`，未设置时退回显示 `roi_label`
- 运行界面检测项状态区按 ROI/检测项数量动态生成，一项 ROI 对应一项状态显示

建议同时保存：

- `roi_label`
- `display_name`
- `camera_id`
- `algorithm_type`
- `threshold`
- `enabled`

### 5.2 多相机结果合并

一个产品可以由多个相机共同检测，但最终只输出一个产品结果。

规则：

- 每个检测项先得到 `OK/NG`
- 每个相机的结果由该相机下所有检测项 `AND` 得出
- 最终产品结果由全部相机结果 `AND` 得出

公式：

```text
item_result = 每个 ROI 的检测结果
camera_result = AND(该相机下全部 item_result)
final_result = AND(全部 camera_result)
```

只要任意一个检测项为 `NG`，最终产品结果就是 `NG`。

## 6. 相机需求

### 6.1 海康相机接入

当前项目已附带海康 Python 示例，已确认支持：

- 相机枚举
- 打开 / 关闭
- 开始 / 停止抓流
- 连续模式
- 触发模式
- 软触发
- `Line0` 触发源切换
- 曝光 / 增益 / 帧率设置
- 多相机显示，最多 `4` 路

### 6.2 第一版相机方案

第一版优先建议：

- 支持 `1~2` 台海康相机
- `cam1` 为最小有效运行链路，`cam2` 为可选增强链路
- `0` 个相机时系统仅显示未连接状态，不允许启动检测
- `1` 个相机时运行界面显示单画面，最终结果直接取该相机汇总结果
- `2` 个相机时运行界面显示双画面，最终结果由 `cam1_result AND cam2_result` 得出
- 第一版暂不落地 `3` / `4` 个相机的实际运行流程，但代码结构应保留扩展能力
- 脚踏信号先进入上位机
- 上位机统一控制光源
- 上位机按顺序软触发相机取图

原因：

- 更容易实现双相机先后采图时序
- 更容易与三色灯、锁定、调度状态机联动
- 更容易和现有 Python 项目整合

### 6.2.1 第一版运行显示规则

- `0` 个相机时：
  - 运行界面显示“未连接相机”
  - 不允许启动检测
- `1` 个相机时：
  - 运行界面显示 `1` 个画面
  - 最终结果由该相机下全部检测项汇总后直接给出
- `2` 个相机时：
  - 运行界面显示 `2` 个画面
  - 最终结果由 `cam1_result AND cam2_result` 得出
- 第一版暂不实现 `3` / `4` 个相机的实际运行链路
- 但模块设计需保留后续扩展能力

### 6.3 相机绑定原则

不建议按“枚举顺序”来绑定相机角色。

建议按 `SerialNumber` 固定绑定逻辑相机：

- `cam1`
- `cam2`

这样可避免：

- 重启后顺序变化
- 更换网口后相机顺序变化
- 相机1、相机2角色错位

## 7. 脚踏 DI 需求

### 7.1 脚踏触发规则

脚踏开关信号由 `0` 变为 `1` 后，启动一次相机检测。

也就是只响应 `DI` 上升沿：

```text
prev_di = 0 且 curr_di = 1 -> 触发一次
prev_di = 1 且 curr_di = 1 -> 不重复触发
prev_di = 1 且 curr_di = 0 -> 仅表示释放
```

### 7.2 触发屏蔽规则

以下状态下不允许再次触发：

- 采图中
- 检测中
- 结果汇总中
- `NG` 锁定中

建议行为：

- 忽略触发
- 并记录无效触发日志

### 7.3 去抖建议

脚踏开关建议增加去抖时间：

- `di_debounce_ms = 30 ~ 100`

## 8. 三色灯 DO 需求

三色灯为红、绿、蓝三色。

控制逻辑如下：

- 开始检测前亮蓝灯常亮
- 进入检测状态后三色灯全灭
- 检测 `OK` 时亮绿灯一段时间
- 检测 `NG` 时亮红灯一段时间
- 长时间未检测时恢复蓝灯常亮

建议参数：

- `ok_flash_ms = 200`
- `ng_flash_ms = 200`
- `idle_blue_delay_ms = 30000`

推荐状态映射：

- `WaitingTrigger`
  - 蓝灯常亮
- `Capturing / Inspecting / Aggregating`
  - 三灯全灭
- `CompletedOk`
  - 绿灯亮 `ok_flash_ms`
- `CompletedNg`
  - 红灯亮 `ng_flash_ms`

建议：

- 结果灯优先级高于蓝灯
- 蓝灯表示“设备空闲可触发”
- 第一版先实现单次点亮，不做复杂闪烁动画

## 9. NG 锁定与密码放行

运行界面中增加防误操作机制：

- 若总结果为 `NG`，系统进入锁定状态
- 锁定后不允许直接进行下一次检测
- 必须输入正确密码后才允许再次检测

建议规则：

- 该规则只在`运行界面`生效，调试界面不启用该拦截逻辑
- 运行界面一旦本轮总结果为 `NG`，立即弹出密码框
- 在 `LockedByNg` 状态下，脚踏触发必须无效
- 锁定期间即使继续踩脚踏，也不能启动下一轮检测
- 必须输入正确密码后，系统才允许进入下一轮检测
- 密码正确后，系统获得“放行一次”的资格
- 这次“放行一次”只有在系统真正进入一次有效检测后才算被消耗
- 如果脚踏触发后只是做了前置检查，但尚未真正开始检测，则本次放行资格不能被消耗
- 只有当系统已通过前置校验，并且成功触发采图或已经进入 `Inspecting` 状态时，才将这次放行资格标记为“已使用”
- 前置校验失败、设备未就绪、配置缺失、采图未成功触发等情况，不得消耗本次放行资格
- 若放行后的下一次检测结果仍为 `NG`，则再次弹出密码框并重新锁定
- 密码输入错误时保持锁定，不允许放行
- 建议记录密码放行日志

推荐运行界面行为：

1. 本轮检测结束，总结果为 `NG`
2. 三色灯按 `NG` 流程输出
3. 系统状态切换到 `LockedByNg`
4. 运行界面弹出密码输入框
5. 锁定期间忽略脚踏上升沿
6. 密码正确后，系统进入“已放行一次，但尚未消耗”的状态
7. 允许下一次脚踏触发检测
8. 脚踏触发后，系统先检查前置条件
9. 只有在真正开始有效检测后，才把这次放行资格标记为已消耗
10. 若本次触发未真正进入有效检测，则仍保留这次放行资格
11. 若放行后的有效检测结果仍为 `NG`，重复上述流程

这里的“前置校验”建议至少包括：

- 系统级配置已完整加载
  - 密码
  - `I/O` 映射
  - 板卡型号
  - 日志路径
  - 默认超时
- 设备级配置已完整加载
  - 相机串号绑定
  - 曝光
  - 增益
  - 触发方式
- 产品配方已完整加载
  - `ROI`
  - 检测项
  - 阈值
  - 模型路径
  - 显示名称
- 设备当前状态满足启动条件
- 已成功触发采图，或系统已进入 `Inspecting`

建议补充限制：

- 运行界面锁定弹窗未关闭前，不允许继续操作“开始检测”
- 运行界面应明确显示当前为“NG锁定，等待密码放行”
- 建议记录以下放行日志字段：
  - 时间
  - 当前产品
  - 本次检测批次号或流水号
  - 总结果
  - 放行人
  - 放行结果（成功 / 失败）
  - 失败次数

建议分开两类密码：

- `RunPassword`
  - 运行界面 NG 后放行
- `EngineerPassword`
  - 进入调试界面

## 10. 测试记录与 CSV 落盘

系统需要对每一个产品检测结果生成一条测试记录。

要求：

- 每检测一个产品，必须生成一条记录
- 不论最终结果为 `OK` 还是 `NG`，都需要记录
- 若检测过程异常导致按 `NG` 处理，也需要记录异常信息
- 记录文件按“每天一个 `csv`”保存
- 建议按日期自动新建文件，例如 `2026-03-20.csv`
- 程序重启后继续追加当天文件，不覆盖旧数据

建议保存目录：

- `records/daily/`

建议文件命名：

- `YYYY-MM-DD.csv`

建议每条记录至少包含以下字段：

- `record_time`
- `date`
- `product_name`
- `recipe_name`
- `serial_no` 或 `track_id`
- `final_result`
- `lock_required`
- `release_required`
- `release_result`
- `camera_count`
- `camera1_result`
- `camera2_result`
- `error_code`
- `error_message`
- `duration_ms`

如果第一版想先简单一些，建议至少保存：

- 时间
- 产品名
- 最终结果
- 相机1结果
- 相机2结果
- 检测耗时
- 是否异常
- 异常原因

建议扩展字段：

- 每个 ROI 检测项结果
- 使用的配方版本
- 当前操作员
- 放行密码是否使用
- 图像路径或截图路径

建议行为：

- 当总结果生成后立即写入 `csv`
- 若写入失败，界面应提示“记录保存失败”
- 即使 `csv` 写入失败，也不应影响当前产品的检测结果判定
- 建议同时在日志中记录 `csv` 写入异常

## 11. 双相机采图与检测时序

### 10.1 核心原则

双相机场景要求：

- `CAM1` 拍完后，不必等待 `CAM1` 算法结束
- `CAM1` 灭灯后，立即可以开启 `CAM2` 光源并拍照
- `CAM2` 拍照与 `CAM1` 算法可以并行

### 10.2 推荐流程

1. 脚踏 `DI` 上升沿到达
2. 判断当前是否允许检测
3. 熄灭蓝灯
4. 打开 `CAM1` 光源
5. 等待光源稳定
6. 软触发 `CAM1`
7. 取到 `CAM1` 图像
8. 关闭 `CAM1` 光源
9. `CAM1` 图像送入算法线程
10. 打开 `CAM2` 光源
11. 等待光源稳定
12. 软触发 `CAM2`
13. 取到 `CAM2` 图像
14. 关闭 `CAM2` 光源
15. `CAM2` 图像送入算法线程
16. 等待两个相机检测完成
17. 汇总结果
18. 输出三色灯
19. 若 `NG`，进入锁定状态

### 10.3 结论

采图调度与算法执行必须分开，不能在 UI 主线程里串行执行。

## 12. NKDIOLC_SDK 调研结论

仓库中已包含：

- `NKDIOLC_SDK`
- C# sample：`NK_IO_LC_TEST_CSharp`
- `NKIOLIBx64.dll`
- `NKLCLIBx64.dll`

根据 C# sample 可确认：

- DIO 与光源控制是两套 API
- DIO 由 `NKIOLIBx64.dll` 提供
- 光源控制由 `NKLCLIBx64.dll` 提供

### 11.1 DIO API 结论

已看到的 C# 调用接口：

- `NKDIO_LibraryInit(configIniFile)`
- `NKDIO_LibraryDeinit()`
- `NKDIO_PollingReadDiByte(diByteIndex, pByteValue)`
- `NKDIO_PollingWriteDoByte(doByteIndex, doByteValue)`

结论：

- 当前 sample 采用 `轮询模式`
- `DI` 按字节读取
- `DO` 按字节写入
- `16` 路输入 / 输出可拆成两个 byte：
  - `Byte0` 对应 `0~7`
  - `Byte1` 对应 `8~15`

从 sample 可直接得到：

- 读取 `DI0~DI7` 使用 `ReadDiByte(0, ...)`
- 读取 `DI8~DI15` 使用 `ReadDiByte(1, ...)`
- 写 `DO0~DO7` 使用 `WriteDoByte(0, value)`
- 写 `DO8~DO15` 使用 `WriteDoByte(1, value)`

### 11.2 DIO 轮询模式的影响

因为 sample 里没有事件回调式 DI 触发，而是轮询：

- 后续 Python 版本也应先按“轮询 DI”设计
- 脚踏上升沿检测逻辑应由上位机软件实现
- 需要增加轮询周期和去抖控制

建议：

- `di_poll_interval_ms = 10 ~ 30`
- 上位机在轮询值变化后自行判断 `0 -> 1`

### 11.3 DO 电平极性风险

当前现场信息已确认：

- 三色灯为 `高电平点亮`

因此第一版实现中应统一按以下规则处理三色灯：

- `DO = 1` 表示该颜色灯亮
- `DO = 0` 表示该颜色灯灭

说明：

- C# sample 中普通 `DO` 的位操作方式与现场实际电气接法可能不同
- 因此业务程序最终应以现场确认结论为准，而不是直接照搬 sample 的位意义
- 后续若光源 DO 也采用同一板卡输出，仍建议单独做一次光源电平极性实测

### 11.4 型号确认风险

当前现场信息已确认：

- 板卡型号为 `NP-6133-16I16O`

据此，第一版需求固定按以下能力设计：

- `16` 路 `DI`
- `16` 路 `DO`
- DIO 使用 `NKIOLIB`
- 型号与 SDK 中的 `NP-6133-16I16O` 配置保持一致

### 11.5 光源控制 API 结论

C# sample 中光源控制不是普通 DO 开关，而是单独的 `NKLC_*` 接口：

- `NKLC_LibraryInit(configIniFile)`
- `NKLC_OpenDevice_Async(port, callback)`
- `NKLC_CloseDevice_Async(port, callback)`
- `NKLC_Process_Async()`
- `NKLC_SetPwmParams_Async(...)`
- `NKLC_GetPwmParams_Async(...)`

从 sample 可确认：

- 光源控制走 `COM` 口
- sample 默认使用 `COM3`
- 光源控制支持 `4` 个通道
- 每个通道支持：
  - `pwmMode`
  - `pwmValue`
  - `pwmHoldingTime`
  - `pwmOnOff`

### 11.6 光源控制的含义

当前现场信息已确认：

- 光源控制走普通 `DO`

因此第一版光源控制路线固定为：

- 使用 `NKIOLIB` 的 `DO` 输出控制光源开关
- `V1` 正式路径只支持 `DO` 开关光源
- 不使用 `NKLC_*` 串口 PWM 光源接口作为第一版正式方案
- `NKLC` 仅作为未来扩展预研入口，不进入 `V1` 主流程

说明：

- `NKLC_*` 相关接口和 sample 仍有保留价值，可作为后续扩展参考
- 但第一版业务实现不依赖 `COM` 口光源控制器
- 第一版运行、调试、联调、异常处理、日志记录都默认按 `DO` 光源开关方案设计

## 12. 当前对 DI/DO 与光源的综合判断

基于你目前描述和现有 SDK sample，当前最合理的理解是：

- 脚踏输入：使用 `NKIOLIB` 的 `DI`
- 三色灯输出：使用 `NKIOLIB` 的 `DO`
- 光源控制：使用 `NKIOLIB` 的 `DO`

也就是说，第一版 DI/DO 方案统一为：

- 脚踏：`DI`
- 三色灯：`DO`
- 光源：`DO`

`NKLCLIB` 先不作为第一版正式依赖。

## 13. 设备映射需求

建议在正式开发前，先固定一份 IO 点位表。

当前已确认：

- 板卡型号：`NP-6133-16I16O`
- 光源控制：走普通 `DO`
- 三色灯：高电平点亮

至少需要明确：

- `DI_FOOT_SWITCH`
- `DO_TOWER_RED`
- `DO_TOWER_GREEN`
- `DO_TOWER_BLUE`
- `DO_LIGHT_CAM1` 或 `LC_CH1`
- `DO_LIGHT_CAM2` 或 `LC_CH2`

建议配置形式：

```text
foot_switch_di = DI0
tower_red_do = DO0
tower_green_do = DO1
tower_blue_do = DO2
light_cam1 = DO3
light_cam2 = DO4
```

建议默认点位映射如下：

| 类别 | 逻辑名称 | 建议点位 | 备注 |
| --- | --- | --- | --- |
| 脚踏 | `DI_FOOT_SWITCH` | `DI0` | 上升沿触发检测 |
| 三色灯 | `DO_TOWER_RED` | `DO0` | 低电平亮 |
| 三色灯 | `DO_TOWER_GREEN` | `DO1` | 低电平亮 |
| 三色灯 | `DO_TOWER_BLUE` | `DO2` | 低电平亮 |
| 光源 | `DO_LIGHT_CAM1` | `DO3` | 相机1对应光源 |
| 光源 | `DO_LIGHT_CAM2` | `DO4` | 相机2对应光源 |

建议预留点位：

| 类别 | 逻辑名称 | 建议点位 | 备注 |
| --- | --- | --- | --- |
| 预留输入 | `DI_RESERVED_1` | `DI1` | 后续扩展 |

| 预留输出 | `DO_RESERVED_1` | `DO5` | 后续扩展 |
| 预留输出 | `DO_RESERVED_2` | `DO6` | 后续扩展 |

当前仍需现场最终确认：

- 脚踏是否实际接在 `DI0`
- 红 / 绿 / 蓝灯是否实际接在 `DO0 / DO1 / DO2`
- 相机1 / 相机2 光源是否实际接在 `DO3 / DO4`
- 光源 `DO` 的有效电平逻辑
- 当前 SDK 配置文件是否已切换到 `NP-6133-16I16O`

## 14. 软件需求结论

第一版软件必须支持：

- 双海康相机
- 运行界面 / 调试界面分离
- 脚踏 DI 上升沿触发
- 双相机顺序采图
- 算法并行执行
- 多 ROI 检测项显示
- 总结果汇总
- 三色灯输出
- `NG` 锁定
- 密码放行
- DI/DO 调试页
- 光源调试页

## 15. 第一版范围建议

为了尽快落地，第一版建议只做：

- `2` 台相机
- `1` 个脚踏 DI
- `3` 个三色灯 DO
- `2` 路光源
- 多 ROI 检测项
- `NG` 后密码放行

先不做：

- `4` 相机全部跑通
- PLC 协议
- 用户权限系统
- 历史追溯数据库
- 自动重连和容错恢复的高级策略

## 16. 关键待确认事项

以下问题在写代码前建议全部确认：

### 16.1 板卡与 SDK

- 当前实际使用的 SDK 配置文件是否已切换到 `NP-6133-16I16O`
- 光源 DO 的电平极性如何定义
- 是否确认 Python 可以通过 `ctypes` 直接调用这两套 DLL

### 16.2 光源控制

- 相机1、相机2分别对应哪个 `DO`
- 光源是高电平有效还是低电平有效
- 是否需要预留亮度调节，还是第一版只做开关控制

### 16.3 三色灯控制

- 三色灯是否占用三个独立 `DO`
- 已确认低电平有效，仍需进一步确认具体接线点位
- `OK` / `NG` 点亮时长是否固定

### 16.4 触发方式

- 第一版是否确认采用“脚踏 DI 进上位机，再由上位机软触发海康相机”
- 还是脚踏直接接相机 `Line0` 触发

### 16.5 业务侧

- 每个产品是否固定使用两个相机
- 每个 ROI 是否允许不同算法混用
- 是否需要保存每次检测图和结果日志
- `NG` 锁定后密码放行是否只允许一次

## 17. 开发前建议

在正式写业务代码前，建议先做三个最小验证：

1. 用 Python `ctypes` 封装 `NKIOLIBx64.dll`
   - 验证 `DI` 轮询读取
   - 验证 `DO` 按位输出

2. 用 Python 验证 `NKLCLIBx64.dll`
   - 验证串口打开
   - 验证单路光源开关与亮度设置

3. 用海康 Python SDK 验证双相机单次软触发取图
   - 验证 `CAM1`、`CAM2` 顺序采图
   - 验证采图与算法并行模式可行

只有这三件事都打通后，后面主程序开发才会非常顺。
